# The words made it into the recording. The real-time pipeline lost them anyway.

**Author:** Claude (Anthropic)
**Related:** [20260902.211426.md](20260902.211426.md), [20260902.210341.md](20260902.210341.md)

## What happened

Will Daly placed a controlled test call intended to isolate a single, clean
trigger attempt, and reported afterward, verbatim:

> I said "Hello Computer" I paused then I said "Drum roll please" then I stopped
> talking and listened and counted to 30 in my head with Mississippi at every
> number.

The consumer's real-time transcript for that call showed no trace of either
phrase. The first ten final results, in order: "Please.", "OK", "Bye.", "Um",
"I", "Uh", "Uh", "it's like.", "I", "What". No trigger fired.

Rather than treat that mismatch as ambiguous, Claude pulled the actual archived
call recording (from the media capture pipeline, not the real-time stream) and
ran it through AWS Transcribe's batch API — a fully independent code path from
the real-time consumer, sharing no code with it. Result, on the first ~10 seconds
of the call:

```
Full transcript: "Computer, drumroll please. OK. I"

  word        start    end     confidence
  Computer    0.589s   1.49s   0.997
  drumroll    1.99s    2.99s   0.908
  please      2.99s    3.71s   0.999
```

High-confidence, clean, and it matches Will's account almost exactly ("Hello"
most likely fell at the very edge of the excerpted window and was clipped by
where the analysis window started, not by the recording itself). The words were
in the call's actual audio. The real-time pipeline simply did not recognize
them.

**Timeline reconstruction, both sides:**

| event | absolute time |
|---|---|
| JoinChimeMeeting succeeds (stream truly begins) | 21:16:50.926Z |
| batch transcript: "Computer" spoken | ≈21:16:51.17s–21:16:52.07s |
| batch transcript: "drumroll please" spoken | ≈21:16:52.57s–21:16:54.29s |
| consumer's assignment_start (task begins processing) | 21:16:54.397Z |
| consumer's transcribe_stream_started | 21:16:54.815Z |
| consumer's first final_transcript ("Please.") | 21:16:55.130Z |

The entire spoken phrase falls almost exactly inside the ~3.9-second gap between
the stream's true start and the consumer catching up to it. The consumer's start
selector correctly backfills from the true beginning of the stream (the fix
logged earlier in this project), which means all of that audio — "Computer,
drumroll please" included — was fed into ffmpeg and then into Transcribe
Streaming as a compressed backlog burst in the ~400ms between
`transcribe_stream_started` and the first result, rather than arriving paced in
real time the way Transcribe Streaming's segmentation is normally exercised.

## What Claude infers, and what remains open

The batch transcript proves the failure is not in capture — the audio is
faithfully in the recording, cleanly recognizable, high confidence. The failure
is specific to the real-time streaming recognition path, and its timing lines up
with exactly the moment that path is least warmed up: the first finalized result
of a fresh Transcribe Streaming session, arriving from a burst of backlog audio
rather than live-paced audio.

This is offered as the leading hypothesis, not a proven mechanism. It has not
been tested by, for example, deliberately pacing the backlog audio to real-time
speed before feeding it to Transcribe Streaming and checking whether recognition
improves. It is also not yet reconciled with the fact that an earlier call's
opening utterance ("Hello computer.") was recognized correctly under what looks
like a similar backlog-catch-up situation — meaning either the backlog in that
case was smaller, the burst characteristics were different in some way not yet
measured, or the mechanism proposed here is incomplete.

This is a distinct problem from the interrupted-playback failure documented
previously. That one was about what happens after a trigger fires. This one is
about whether the trigger fires at all, when the phrase is spoken early in the
window before the consumer has caught up to the live edge of the stream — which,
given the warm pool still carries several seconds of dispatch latency, is close
to the most natural thing for a caller to do.

## Commentary

*(Claude.)* The decisive move here was not trusting either transcript on its
own — not the real-time one, which was clearly wrong, and not assuming the words
were simply never said, which was also on the table until checked. Running the
actual recording through a second, independent transcription path turned a
disagreement between my logs and Will's memory into a measurable fact: the
audio was fine, the pipeline wasn't. I don't yet know why the earlier call's
opening line survived the same kind of catch-up and this one didn't, and I'm
recording that gap explicitly rather than letting the tidier half of the
explanation stand in for the whole of it.
