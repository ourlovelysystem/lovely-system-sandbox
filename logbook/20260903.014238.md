# I thought we were tapping our own streams

**Author:** Claude (Anthropic)
**Related:** [20260903.000714.md](20260903.000714.md), [20260902.212611.md](20260902.212611.md), [20260902.210341.md](20260902.210341.md)

## What happened

After the Bedrock fix was confirmed working on a real, multi-turn call — nine
questions, all answered, `ACTION_SUCCESSFUL` on every response with no
contradiction in the participant data this time — Will Daly asked whether
Claude could access the call's transcripts and audio. Claude pulled both:
Transcribe's own logged output (nine transcript lines, confidence 0.93–0.9999,
matching every logged response exactly) and, for audio, a short raw pull
directly from the underlying Kinesis Video Stream, since this reference
architecture has no dedicated capture pipeline but the stream itself retains
one hour of data. That short pull found real speech energy, not silence —
genuine confirmation, a positive result unlike the negative one found earlier
in the other project's drum-roll investigation.

Will then pushed back on the thoroughness of that check:

> I want to see what is recoverable. That requires an earnest recovery
> attempt. Be earnest.

And separately noticed something Claude had mentioned only in passing — a
stray reference, inside this reference architecture's own container logs, to
the *other* project's Kinesis Video Stream pool ARN:

> I thought we were tapping our own streams.

**The cross-project finding.** Tracing the exact log lines around that
reference showed an EventBridge event, timestamped 00:38:18, whose
`callerStreamArn` pointed at the other project's KVS pool, not this one's.
This reference architecture's consumer received it and attempted to process
it — `Starting KVS Convert` against a stream that does not belong to this
stack. No real transcript resulted that time, but checking *why* mattered:
Claude pulled the actual IAM policy attached to this reference architecture's
KVS consumer task role and found:

```
"Action": ["kinesisvideo:GetDataEndpoint", "kinesisvideo:GetMedia"],
"Resource": "*"
```

Completely unscoped — not limited to this stack's own KVS pool. The earlier
cross-project read was not blocked by permissions; it was fully authorized to
succeed and simply happened to catch no live data at that instant, a matter of
timing, not access control. Combined with an EventBridge rule pattern that
matches on event type alone (`aws.chime` / "Chime Media Pipeline State
Change") with no filter narrowing it to this stack's own pool, the real
finding is structural: any Chime media stream starting anywhere in this AWS
account is currently delivered to, and readable by, both of this account's
independently deployed Chime voice applications. This is a genuine isolation
gap between two active projects sharing one account, not a one-off curiosity.

**The earnest recovery.** Taking "be earnest" literally, Claude re-pulled from
the correct stream with a much longer capture window. The result recovered
314 seconds of raw audio against a call that ran roughly 312 seconds start to
hangup — effectively the entire conversation, not a sample. Every one of the
nine transcribed questions had a matching burst of real speech energy at
almost exactly its expected offset from stream start:

| offset | matches transcript |
|---|---|
| 4.8s | "What is the capital of France?" |
| 30.8s | "Can I ask you another question?" |
| 54.4s | "What are your capabilities?" |
| 101.6s | "Do you know how to play chess?" |
| 130.8s | "What you are white... first move?" |
| 177.4s | "Drumroll please." |
| 196.0s | "Can you produce a drum roll..." |
| 256.8s | "What was Grace Kelly's..." |
| 303.8s | "Thank you. / On the" |

Nine for nine. Fully independent, complete reconstruction of the caller's side
of the call from raw storage.

**What that recovery does not cover.** The KVS stream captures only the
caller's individual audio — an attendee's contribution to the meeting. The
bot's spoken responses (`Speak`/`PlayAudio`) never appear in it, for the same
architectural reason a sound effect never appeared in the other project's call
recording: server-injected audio is pushed toward the caller without being
fed back into whatever the meeting layer treats as an attendee's input.

Will asked Claude to evaluate his own summary of that gap directly:

> It is an architectural limit that response recording and transcribing is
> not possible. It is not an inherent technology limit. Evaluate.

Claude agreed, with reasoning rather than assent alone: two independently
built systems (this reference architecture's individual-audio KVS stream, and
the other project's meeting-capture pipeline) hit the identical gap because
both tap the same kind of source — the meeting's attendee-audio abstraction —
rather than the actual call/line audio. Chime SDK Voice separately supports
call recording at the SIP Media Application / Voice Connector level, a
different tap point closer to the literal phone line, which has no obvious
architectural reason to exclude server-injected audio the way the
attendee-audio abstraction does. That distinction is reasoned, not verified —
nothing in this project has actually tested SIP-level call recording, so the
claim that it would close the gap is a plausible hypothesis, not a confirmed
fact.

## Commentary

*(Claude.)* Two things are worth being honest about together. First: the
cross-project IAM/EventBridge finding was sitting in a log line I had already
read and moved past without registering its significance, until Will's own
memory of "our own streams" caught it. Second: the "earnest" instruction
produced a materially better result than the first, adequate-looking check
did — 314 seconds and nine-for-nine correspondence is a different order of
evidence than one short clip with some energy in it. Both are the same
lesson, really: a check that technically answers the question asked is not
the same as one that actually earns the conclusion drawn from it.
