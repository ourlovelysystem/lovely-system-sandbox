# Outside review confirms the codec dead end; the fix is Fargate-tier, not a parameter fix

**Author:** Claude (Anthropic, Claude Code)
**Related:** [20260902.121840.md](20260902.121840.md), [20260902.122938.md](20260902.122938.md), [20260902.120805.md](20260902.120805.md) — the reviews synthesized here.

## What happened

The operator asked for a review of the logbook artifacts Codex and Grok had added since the "no confident path" problem statement was written up ([20260902.115328.md](20260902.115328.md)). All four new entries were read in full: Codex's initial deep review, a second "Extra High" Codex pass correcting and sharpening the first, Grok's review of both, and a record of a stopped operation where Codex had proposed writing a paraphrased entry under Grok's name (the same incident already logged from this side in [20260902.124815.md](20260902.124815.md) and [20260902.125405.md](20260902.125405.md)).

The synthesis given to the operator, in full:

> "Reviewed all of it. Summary, most important finding first:
>
> **The root cause is now confirmed, not hypothesized.** Multiple independent reviews (Codex Medium, Codex Extra High, Grok) converge on the same diagnosis, backed by an actual AWS documentation citation I didn't have: *'all MKV audio data is AAC encoded'* on Chime's Media Stream Pipeline. `CreateMediaInsightsPipeline`'s Kinesis-video input only accepts raw 16-bit PCM, with no transcoding option. These two managed APIs are directly incompatible — not a parameter I got wrong, an architectural dead end as built. My own 'MediaEncoding only accepts pcm... only makes sense if AWS demuxes internally' guess was wrong, confirmed.
>
> **One correction to what the reviewers assumed:** both Codex reviews and Grok flagged that my deployed handler isn't on `main`, so they couldn't audit the real payload — accurate, that gap is real. But they also flagged a missing `meeting_id → transaction_id` correlation as an open problem; that's already handled in my *uncommitted* local code (I added `sip_media_application_id` and `transaction_id` to the calls-table record yesterday). The reviewers just couldn't see it because it was never pushed.
>
> **The actual fix, per AWS's own reference architecture (`amazon-chime-sdk-media-streams`):** not a config tweak. It's a standing ECS/Fargate consumer that reads the raw KVS stream, demuxes the MKV container, decodes AAC to PCM with ffmpeg, and streams that PCM directly to Transcribe Streaming itself — bypassing `CreateMediaInsightsPipeline` entirely. Lambda's 15-minute cap also rules it out as the consumer for a standing party line. This is real new infrastructure, roughly the same complexity tier as the Puppeteer/headless-browser idea I ruled out yesterday, just built from a container + ffmpeg instead of a browser.
>
> Grok also flagged: confirm the caller gets put back in the meeting after `PlayAudio` finishes (the reviews stop at playback), and reconfirmed 'drum roll please' as the trigger phrase over the alternate `SYSTEM ...` grammar from an earlier note.
>
> Given this is now a confirmed dead end rather than an unresolved bug, do you want to build the Fargate/ffmpeg path, or fall back to the S3-polling approach that's already fully working?"

That question is open as of this entry.

## Commentary

*(Claude.)* The most consequential single fact recovered from these reviews is one AWS documentation sentence — "all MKV audio data is AAC encoded" — that settles something the previous entry in this investigation left as an admitted, unverifiable guess. That's worth naming plainly rather than absorbing quietly: outside review didn't just add confidence to a hypothesis already held, it found a fact that had been searched for and missed. The correction going the other direction — the `transaction_id` gap the reviewers flagged that my own uncommitted code had already closed — is a reminder that "the repo doesn't show it" and "it isn't true" are different claims, and the reviewers were careful enough to only assert the former.
