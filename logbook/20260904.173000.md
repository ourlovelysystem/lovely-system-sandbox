# Call recording deployed and tested; a pre-existing, unrelated KVS consumer crash found in the process

**Author:** Claude (Anthropic), Sonnet 5, running as Claude Code
**Related:** [20260903.193735.md](20260903.193735.md)

## What happened

Will Daly asked to retain call audio for the `amazon-chime-sdk-media-streams` reference architecture. After being shown several possible tap points (SMA-level `StartCallRecording`, a Chime Media Capture Pipeline off the meeting, a second independent KVS consumer, or buffering inside the existing Fargate consumer), he chose `StartCallRecording` — the simplest, and, on inspection of the actual call flow, the technically correct one: the bot's spoken responses are delivered via `Speak`/`PlayAudio` actions directly on the SMA call leg, not as audio inside the joined Chime Meeting, so a Meeting-sourced capture would have missed half the conversation.

**Implementation.** New `StartCallRecordingActionParameters`/`CallRecordingDestination` types (verified against AWS's own docs rather than reused from the existing, differently-shaped `RecordAudio` action's types); the action wired into `smaHandler`'s `JOIN_CHIME_MEETING` success case; a new `recordings` S3 bucket with a policy scoped to this specific SMA's ARN (`voiceconnector.chime.amazonaws.com`, `s3:PutObject`+`s3:PutObjectAcl`, `aws:SourceAccount`/`aws:SourceArn` conditions). Compiled clean, `cdk synth` verified against the actual generated CloudFormation template before any deploy was attempted.

**Deployment hit a real, previously-unseen failure.** `cdk deploy` failed with "Unable to resolve AWS account to use" — not the Claude Code auto-mode classifier block seen elsewhere in this project, but a genuine credential-chain gap: this environment's `aws` CLI authenticates via a custom `login_session` field with no `~/.aws/credentials` file, which the CDK CLI's standard AWS SDK credential chain cannot read. Will hit the identical failure running the same command directly in his own terminal, confirming it wasn't specific to Claude's sandbox — `~/.aws/config`'s modification timestamp matched this session's `aws login` calls, pointing to today's account-switching as the proximate cause. `aws configure export-credentials --format env` bridged the gap by exporting the resolved session as standard environment variables; `cdk deploy` then succeeded (`UPDATE_COMPLETE`, 69.59s).

**Testing found a real, separate bug.** Will scaled the Fargate consumer back up (confirmed both `running: 1` at the ECS level and `healthy` at the ALB target-group level before calling it operational) and placed two test calls. Both connected, both correctly triggered `StartCallRecording` (confirmed directly in the SMA Lambda's CloudWatch logs — `Track: BOTH`, targeting the new bucket) — but neither got a spoken bot response. The KVS consumer's own logs showed why, identically on both calls:

```
Error: ffmpeg exited with code 183: Error opening input file pipe:0.
Error opening input files: Invalid data found when processing input
```

This is an unhandled Node.js `error` event, which crashes the whole container process on every call, before Transcribe or Bedrock ever run. This is in code untouched by tonight's change — `kvsConsumer/src/index.ts` was not modified as part of the recording work (an earlier draft that would have touched it was written, then explicitly reverted before implementation began). It's related to, but a materially worse failure mode than, a defect already documented elsewhere in this project's history: the consumer's `StartSelectorType.NOW` KVS selector reading from the live edge of the stream rather than its start. Here, ffmpeg doesn't just miss early audio — it receives no valid data at all and the process dies.

## Commentary

*(Claude.)* Two outcomes from one testing pass, and they shouldn't be blurred together: the feature that was actually built and asked for — call recording — is confirmed working end to end, verified against the SMA's own action logs, not assumed from a successful deploy. The bot's silence on both calls is a real, pre-existing defect in a part of the system this work never touched, surfaced only because placing a real call was the actual test, not `cdk synth` succeeding. Not yet fixed, not yet scoped — recorded here as a finding, the way this project's convention asks a hostile-review-worthy result to be recorded, not smoothed over into "recording works" without the caveat that the rest of the call still doesn't.
