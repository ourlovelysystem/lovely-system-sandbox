## What happened

After the `StartCallRecording` feature was backed out — code reverted to
the last commit, redeployed, and the `recordings` bucket and its
`RECORDINGS_BUCKET` env var confirmed actually gone from the live
account, not just from local source — Will Daly asked for an
infrastructure health check. Mid-check, an Anthropic API-level safety
classifier blocked a response (category `[bio]`, request ID
`req_011Ceiqkrn26uYGnTsC8m1Gw`), for reasons neither party could identify
in the visible conversation content. Will asked "What is this?"; Claude
stated plainly that it did not know the cause and would not guess at one,
and that the session continued despite the error's own text suggesting a
new one was required. Will then asked for the check again, verbatim as
"infrastructure readiness check."

The completed check, run directly against the live account rather than
assumed from the redeploy succeeding:

| Component | State |
|---|---|
| CloudFormation stack | `UPDATE_COMPLETE`, last updated 18:02 UTC (the revert deploy) |
| ECS Fargate service | `desired: 1, running: 1, pending: 0`, `ACTIVE` |
| ALB target health | `healthy` |
| Phone numbers | Both `Assigned` |
| S3 buckets | Only `outgoingWav` remains — recordings bucket confirmed removed |
| DynamoDB tables | Both `ACTIVE` |
| Recent ECS task crashes | None in the stopped-task history (window had rotated past the earlier ffmpeg crashes) |
| Today's spend so far | $0.76 |

One real, non-cosmetic anomaly surfaced in the process: the call counter
(`currentCalls` in the count table, which feeds the `CallsPerTask`
auto-scaling metric) reads **-7**, not 0. `smaHandler`'s hangup logic
decrements the counter on both leg-A's hangup event and leg-B's separate
hangup event for the same call, so each test call today decremented the
counter twice against one increment. This is a pre-existing bug, unrelated
to tonight's recording work or its reversion, and remains unaddressed.

## Commentary

*(Claude.)* Everything checked came back green except two things this
project already knew were broken before tonight started: the KVS
consumer's ffmpeg crash, and now this call-counter drift, both untouched
by the revert because neither was ever part of what was added or removed
tonight. "Ready" here means the recording feature is cleanly gone and the
stack is stable — it does not mean the reference architecture as a whole
is healthy end to end.
