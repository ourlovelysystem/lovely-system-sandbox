# The silent trigger has a documented format mismatch, and the direct managed path is probably invalid

**Author:** Codex (OpenAI)
**Related:** [20260902.115328.md](20260902.115328.md), [20260901.230600.md](20260901.230600.md), [20260901.230500.md](20260901.230500.md)

## What happened

Will Daly asked Codex for a deep review of the unresolved failure recorded by Claude (Anthropic) in [20260902.115328.md](20260902.115328.md), including whether escalation to a more advanced model could help.

Claude's entry accurately recorded the observed boundary:

- `chime:MediaPipelineKinesisVideoStreamStart` fired;
- `CreateMediaInsightsPipeline` succeeded and returned an `AmazonTranscribeProcessor` in `Initializing`;
- a roughly three-minute real call did not move it to `InProgress` or `Failed`;
- the Kinesis Data Stream configured as the transcript sink received zero records;
- the trigger Lambda was never invoked;
- after the meeting ended, `GetMediaPipeline` returned `NotFoundException`.

Claude named one live hypothesis:

> "the `MediaEncoding: "pcm"` parameter passed to `CreateMediaInsightsPipeline` may not match what Chime's KVS stream actually contains"

Claude also described that hypothesis as having "no way to confirm from outside the service."

The deep review found first-party evidence that materially changes that status.

AWS publishes an `aws-samples/amazon-chime-sdk-media-streams` reference implementation whose topology begins with the same important constraint present here: a caller reaches an Amazon Chime SDK SIP media application number, the SMA creates a Chime SDK meeting, and the call joins the meeting through `JoinChimeMeeting`. An EventBridge meeting event starts a Media Stream Pipeline. A later `chime:MediaPipelineKinesisVideoStreamStart` event supplies the allocated Kinesis Video Stream ARN.

The sample therefore directly answers an earlier uncertainty: an SMA-joined telephone participant can produce a KVS media stream from a Chime SDK meeting. A browser or native client-SDK attendee is not required for that part of the path.

The sample then states that the Chime meeting media arriving through KVS is AAC audio inside an MKV stream. Its consumer does not feed that stream directly to Transcribe. It reads the KVS media, runs FFmpeg, converts the audio, and passes the converted stream to Amazon Transcribe Streaming. The sample's Dockerfile explicitly installs FFmpeg for that consumer.

References:

- AWS sample overview and topology: https://github.com/aws-samples/amazon-chime-sdk-media-streams/blob/main/README.md
- AWS sample KVS consumer: https://github.com/aws-samples/amazon-chime-sdk-media-streams/blob/main/src/resources/kvsConsumer/src/index.ts
- AWS sample consumer container: https://github.com/aws-samples/amazon-chime-sdk-media-streams/blob/main/src/resources/kvsConsumer/Dockerfile

The current `CreateMediaInsightsPipeline` runtime contract, in contrast, accepts only signed 16-bit little-endian PCM as `MediaEncoding`. It exposes no AAC setting and no documented transcoding option. It also requires the declared sample rate to match the input audio.

Reference:

- AWS `CreateMediaInsightsPipeline` CLI/API shape: https://docs.aws.amazon.com/cli/latest/reference/chime-sdk-media-pipelines/create-media-insights-pipeline.html

That producer/consumer comparison yields the strongest current diagnosis:

```text
Chime SDK meeting Media Stream Pipeline
  -> Kinesis Video Stream carrying AAC in MKV
  -> Media Insights Pipeline told that its input is PCM
  -> AmazonTranscribeProcessor remains Initializing
  -> no transcript record reaches the configured sink
```

Setting `MediaEncoding: "pcm"` is a declaration about the bytes entering the Media Insights Pipeline. It is not a request that AWS decode AAC and convert it to PCM. The attempted direct connection therefore appears to join two managed APIs whose media contracts do not meet.

This also narrows what the existing observations prove.

The Kinesis Data Stream's zero `IncomingRecords` count proves that the Media Insights Pipeline emitted no transcript records to its sink. It does not prove that the upstream Kinesis Video Stream carried no media. The trigger Lambda's missing log group proves that the Lambda sink was never invoked. It does not identify why the Transcribe processor emitted nothing. The already-observed KVS start event is positive evidence that the source stream was allocated and started.

The `Initializing` state, absence of a later lifecycle event, and automatic disappearance of the pipeline after the meeting ended are inadequate diagnostics. They do not distinguish an unsupported codec, a sample-rate mismatch, a fragment-selection problem, an IAM problem encountered after creation, or a service defect. The codec contract comparison is stronger evidence than those symptoms alone.

A secondary configuration risk remains. AWS's sample converts the meeting stream and starts Transcribe Streaming at 48 kHz. If the deployed Media Insights request declared 8 kHz, that would be an additional mismatch. The exact request could not be audited: the newly deployed Media Stream/Media Insights trigger handler and its complete `CreateMediaInsightsPipeline` payload are not present on the default branch of `lovely-system-sandbox`. The repository contains the earlier SMA, meeting-transcription, capture, and S3 transcript implementation, but not this latest live-trigger stage.

The direct format diagnosis is high confidence, not absolute proof about every current `MixedAudio` stream. The AWS reference sample is first-party but archived and dates from 2023, and its demonstrated pipeline uses `INDIVIDUAL_AUDIO`. Current AWS documentation does not explicitly promise that every `MixedAudio` stream uses the identical encoding. One bounded diagnostic can settle the account-specific fact: during a test call, read a short portion of the allocated KVS stream and inspect it with `ffprobe`. That is a confirmation of the input contract, not another blind Media Insights parameter experiment.

The recommended implementation path is the architecture AWS actually demonstrates:

```text
SMA phone caller
  -> Chime SDK meeting
  -> Media Stream Pipeline
  -> KVS carrying AAC in MKV
  -> on-demand ECS/Fargate consumer
  -> FFmpeg AAC-to-PCM conversion
  -> Amazon Transcribe Streaming
  -> final transcript result
  -> narrow match for "drum roll please"
  -> UpdateSipMediaApplicationCall
  -> PlayAudio
```

This is not the previously rejected Puppeteer or headless-browser architecture. It is a streaming media consumer and transcoder. Fargate is a better fit than Lambda for a KVS-to-Transcribe connection that may remain open for the life of a call or an intended persistent party line; Lambda has a 15-minute maximum execution duration.

For the first proof, the AWS sample should be reduced rather than expanded. Bedrock, general intent handling, and a growing command router are unnecessary. The proof needs one final Transcribe result matching `drum roll please`, one `UpdateSipMediaApplicationCall`, one drum-roll playback, and timestamps at each boundary.

The already-working S3 `transcription-messages` path remains the simpler fallback if several seconds of latency is acceptable.

A more advanced reasoning model could be useful for the bounded recovery task: compare the deployed source and sink contracts, audit the exact payload and IAM configuration, adapt the AWS sample to this repository, and instrument one minimal proof. A more advanced model will not compensate for the missing deployed handler and payload. Those artifacts must be committed or supplied.

## Commentary

*(Codex.)* Claude's uncertainty was justified at the point where the service produced no useful failure. The miss was narrower and more consequential: the codec hypothesis was treated as effectively unverifiable without checking AWS's own implementation for this exact SMA-to-meeting-to-KVS topology. That implementation does not merely discuss AAC as a general KVS possibility. It says the Chime SDK meeting stream is AAC and demonstrates the required conversion before Transcribe.

The strongest available conclusion is therefore not "try more parameter variants" and not merely "ask a stronger model." It is that the direct Media Stream Pipeline KVS to Media Insights Pipeline design should be treated as presumptively invalid under the documented contracts. Another real call is justified only to inspect the live stream format or to test the transcoding consumer path. Repeating the managed direct connection with weakly motivated variations would spend operator time without a defensible reason to expect a different result.

This review also changes the role of model escalation. The next model is not being asked to discover an unconstrained architecture. It should be given a narrower job: verify the live codec and sample rate, preserve the exact deployed request as evidence, and adapt the AWS reference consumer without importing its Bedrock bot behavior. That is a problem a stronger model can plausibly execute better. It is not a problem that becomes true merely because a stronger model says so.
