# Extra High review: the codec incompatibility is definitive, and the return path needs correlation state

**Author:** Codex (OpenAI), GPT-5.6 Sol Extra High
**Related:** [20260902.115328.md](20260902.115328.md), [20260902.120805.md](20260902.120805.md)

## What happened

The Claude entry recorded a useful boundary: the Chime media-stream pipeline reached `chime:MediaPipelineKinesisVideoStreamStart`, and `CreateMediaInsightsPipeline` returned a pipeline in `Initializing`, but no transcript record reached the Kinesis Data Stream and the downstream trigger Lambda was never invoked.

A GPT-5.6 Sol Medium review identified an AAC-versus-PCM boundary and recommended a KVS consumer that decodes the Chime stream before sending it to Transcribe Streaming. This Extra High review re-read both entries, checked the current AWS contracts and sample implementation, and inspected the committed partyline handler.

The Medium review's central diagnosis survives. It can now be stated more strongly: **the direct Media Stream Pipeline KVS → Media Insights Pipeline Transcribe configuration connects two documented interfaces with incompatible audio formats.**

AWS's current media-stream-pipeline documentation says that the pipeline stores media as Matroska and that **all MKV audio data is AAC encoded**. The `CreateMediaInsightsPipeline` Kinesis-video runtime configuration accepts only signed 16-bit little-endian PCM and requires the declared sample rate to match the input. The Chime meeting stream is therefore not a valid direct source for that Transcribe processor.

Successful creation of the Media Insights Pipeline does not prove media compatibility. It proves that the control-plane request passed validation and created resources. The observed `Initializing` state, zero downstream records, and absent downstream invocation are consistent with the documented data-plane mismatch.

## Corrections to 20260902.120805.md

The earlier review said:

> Current AWS documentation does not explicitly promise that every `MixedAudio` stream uses the identical encoding.

That caveat is incorrect. The current AWS documentation makes the statement for media stream pipeline MKV audio generally: all of it is AAC encoded. This is not merely an inference from the archived `INDIVIDUAL_AUDIO` sample.

The earlier review therefore also proposed an unnecessary next experiment:

> One bounded codec test before building the replacement path.

A live `ffprobe` inspection may still be useful to confirm operational details such as sample rate, channel layout, track selection, and fragment handling, but another paid call is not needed to establish the codec. The codec is documented as AAC. The next live call should test a working decoder/transcription bridge, not re-prove AAC.

The earlier review said:

> The trigger Lambda's missing log group proves that the Lambda sink was never invoked.

The evidence proves only that the downstream trigger Lambda was never invoked. The input entry describes a Kinesis Data Stream with zero `IncomingRecords` and a Lambda downstream of it; without the exact deployed Media Insights configuration, it should not have been labeled a Media Insights `LambdaFunctionSink`. The zero-record metric places the silence at or before the Kinesis Data Stream sink.

The earlier review referred to the pipeline's “automatic disappearance” after the call. The recorded evidence is only that `GetMediaPipeline` returned `NotFoundException` after the meeting closed. That does not establish whether AWS lifecycle behavior, application cleanup, or another actor deleted it. This uncertainty does not affect the codec diagnosis.

## Material addition: the command return path needs durable call correlation

Decoding and transcription are not the entire command loop.

`UpdateSipMediaApplicationCall` requires the SIP Media Application ID and the active call's `TransactionId`. For an inbound call, that transaction ID arrives in the initial SMA event. The Kinesis-video start event and the media consumer, however, identify the Chime meeting by `meetingId`.

The committed partyline handler currently stores `call_id`, `meeting_id`, `pipeline_id`, and `created_at`. It does not store `transaction_id`. It is keyed by call ID, while the media side naturally starts with a meeting ID.

A working voice-command return path therefore needs a durable lookup such as:

- a record keyed by `meeting_id` containing `transaction_id`, `call_id`, and `sip_media_application_id`; or
- the same fields on the existing call record plus an index or other reliable lookup by `meeting_id`.

The AWS sample implements this exact control-plane bridge: it records `meetingId → transactionId`, then the KVS consumer resolves the ongoing call before invoking `UpdateSipMediaApplicationCall`. If the deployed but uncommitted Lovely System handler already records that mapping, it should be verified and committed; the repository default branch does not show it.

## Material addition: do not copy the archived sample blindly

The AWS `amazon-chime-sdk-media-streams` sample remains valuable because it demonstrates the same broad topology: an SMA-joined caller, a Chime media stream pipeline, a KVS consumer, streaming transcription, and an SMA call update.

Two details require deliberate treatment:

1. The sample README describes AAC → Opus, while the current consumer source converts AAC to raw `pcm_s16le` and starts Transcribe Streaming with `MediaEncoding.PCM` at 48 kHz. The implementation should pin and test one explicit format chain rather than copying a prose snippet.
2. The KVS start event supplies `startFragmentNumber`, but the sample consumer uses a `NOW` selector. That creates a possible startup gap between the event and consumer attachment. The replacement should not silently discard the supplied start marker; it should choose and test a fragment/timestamp selector with the intended replay semantics.

The sample is archived, so its architecture is evidence and starter code, not a maintained contract. Current AWS documentation should govern the media format and API behavior.

## Updated implementation boundary

Do not spend another call on the direct Media Insights configuration. Build the explicit media bridge first:

1. On the inbound SMA event, durably associate `meeting_id` with `transaction_id`, `call_id`, and the SIP Media Application ID.
2. Start the meeting Media Stream Pipeline and retain its pipeline ID for teardown.
3. On `chime:MediaPipelineKinesisVideoStreamStart`, start a bounded ECS/Fargate consumer with the KVS ARN, meeting ID, and intentional fragment selector.
4. Parse the MKV fragments and decode AAC to signed 16-bit little-endian PCM with an explicitly verified sample rate and channel layout.
5. Stream that PCM to Amazon Transcribe Streaming.
6. Evaluate only final transcript results; normalize the narrow command phrase, deduplicate repeats, and apply a cooldown.
7. Resolve the meeting-to-call mapping and invoke `UpdateSipMediaApplicationCall`.
8. Handle the resulting SMA update event with `PlayAudio`, then return to the conference.
9. Tear down the consumer and media pipeline on hangup, timeout, or explicit stop, and emit stage-specific metrics.

The first new end-to-end proof should establish:

- KVS bytes were read;
- AAC frames were decoded;
- PCM bytes entered Transcribe Streaming;
- a final transcript result arrived;
- the phrase matcher fired once;
- the correct transaction ID was resolved;
- `UpdateSipMediaApplicationCall` succeeded; and
- the caller heard the requested audio.

A per-stage ledger is more useful than a final “silent” symptom. At minimum, record meeting ID, KVS fragment position, decoded-byte count, Transcribe session ID, final utterance, match decision, transaction ID lookup result, SMA update request ID, and playback result.

## Commentary

The Medium review found the correct root cause and the right class of replacement. The important changes from this review are:

- confidence increases from “probably invalid” to a documented producer/consumer incompatibility;
- the `MixedAudio` caveat is removed;
- the proposed codec-only proof call is removed;
- two overstatements about the Lambda role and pipeline deletion are corrected;
- the missing `meetingId → transactionId` control-plane mapping is made explicit; and
- fragment-start behavior and the sample's README/source divergence are called out before implementation.

A more intensive model pass was helpful here, but the improvement came from locating a current AWS statement broad enough to cover `MixedAudio` and then tracing the command all the way back to the live SMA transaction. The model label is not the evidence; the contracts and source code are.
