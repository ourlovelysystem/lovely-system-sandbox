# Real-time trigger fires end to end; audio playback blocked, then a second, distinct failure appears

**Author:** Claude (Anthropic)
**Related:** [20260902.194534.md](20260902.194534.md)

## What happened

Following the Deletion Council's close, work resumed on the real-time voice-trigger
pipeline (Kinesis Video Streams → ffmpeg decode → Amazon Transcribe Streaming →
phrase match → `UpdateSipMediaApplicationCall`). A prior fix (matching the trigger
phrase against a normalized, punctuation-stripped transcript instead of an exact
string) had been built and pushed but not yet tested against a live call.

Will Daly placed a test call. The full chain worked for the first time: the
consumer correctly transcribed the phrase, matched it, and fired the trigger. The
SMA function received the update and attempted to play the audio effect — and
failed:

> `ACTION_FAILED / PlayAudio / InvalidAudioSource: "Invalid content type audio/x-wav"`

The audio asset in S3 was stored with `ContentType: audio/x-wav`. Chime's
`PlayAudio` action rejects that MIME type outright; it wants `audio/wav`. Fixed by
rewriting the object's metadata in place via `s3api copy-object` with
`--metadata-directive REPLACE` — no rebuild, no redeploy, no re-upload of the
asset itself. The underlying audio format (16-bit PCM, mono, 8kHz) was confirmed
correct by direct inspection; only the stored MIME type was wrong.

Will called again to confirm. The content-type error did not recur. But a new,
different failure took its place:

> `ACTION_FAILED / PlayAudio / CallAlreadyDisconnected: "Call is already disconnected."`

Reading the consumer's transcript log against wall-clock timestamps: the trigger
phrase was spoken early in the call, matched immediately and correctly — but the
resulting `UpdateSipMediaApplicationCall` did not reach the SMA function until
roughly 26 seconds after the meeting join. By then Will had already hung up. The
call itself was never at fault; the pipeline was simply too slow to catch it while
he was still on the line.

The proximate cause is the same one identified earlier in this project: each call
cold-starts a brand-new Fargate task (image pull, container boot) before the
consumer can begin capturing audio at all. That cold start alone eats most of a
30-second window. Right now that cost is paid on every single call, because a
consumer task is only launched after the stream-start event fires — there is no
warm capacity waiting for it.

Two remediation paths were proposed and not yet chosen or built: keep a warm pool
of idle consumer tasks ready to attach to a stream instantly, or replace the
per-call `RunTask` launch with a long-running ECS service that is always up and
picks up new streams as they arrive. Will has not yet directed which path to take,
or whether to place another call first to further characterize the latency before
committing to an architecture change.

## Commentary

*(Claude.)* Two real bugs, back to back, each found only by reading actual
CloudWatch logs against actual timestamps rather than trusting the code's own
apparent correctness — consistent with this project's established discipline of
verifying against real AWS state rather than assumption. The first was a one-line
metadata fix. The second is not: it's a structural latency problem in the
architecture itself, and fixing it means changing how the consumer task is
provisioned, not patching a value. I don't yet know which of the two proposed
paths is right, or whether there's a simpler third option I haven't considered.
