# Auth Demo: Shared Cognito Pool, PKCE, and a Real Bug in Claim Parsing

**Author:** Claude (Anthropic, Claude Code)
**Related:** [docs/decisions/README.md](../docs/decisions/README.md), the journal app work logged in this same repo's history

## What happened

The operator asked for a simple app demonstrating the reusable social-login pattern discussed earlier: build using the existing shared Cognito user pool (`lovely-system-users`), support the account's configured providers (Google, Login with Amazon) without re-registering anything with either provider, and land the user on a page showing who the system knows them to be plus their session attributes.

Built as a pure static page — no Lambda, no API Gateway, no backend at all. A new Cognito app client (`lovely-system-sandbox-authdemo-web`) was created in the existing pool with both providers enabled, configured as a public client using PKCE rather than a client secret. The page redirects to Cognito's Hosted UI, exchanges the returned authorization code for tokens directly via `fetch()` to the `/oauth2/token` endpoint, and renders the decoded ID token claims. Deployed to a new Amplify app at `main.d1qro6ew8rw857.amplifyapp.com`.

First real login attempt failed: "Sign-in failed: '[object Object]' is not valid JSON." The cause was traced directly from the error text rather than guessed at: `JSON.parse()` produces that exact message when given an array containing one object, because the array gets coerced to a string first. The code assumed the ID token's `identities` claim was a JSON-encoded *string* — a format seen earlier in this session on a *different* API (`cognito-idp list-users`, where `identities` genuinely is a stringified JSON value on the user record). The actual ID token encodes the same claim as a real JSON array, not a string. The assumption was generalized from one API's format to another without checking the token itself.

Fixed with a small helper that accepts either shape (string or already-parsed array/object) rather than assuming one. Redeployed, verified the fix was actually live before telling the operator to retry, and confirmed: **"Works good."**

## Commentary

*(Claude.)* The bug is a clean example of a failure mode worth naming precisely: not a wrong guess made under uncertainty, but a correct fact about one system (the `list-users` API's string-encoded `identities`) applied without verification to a different system (the ID token's own claim encoding) that only superficially resembled it. Both are "Cognito data with a field called `identities`" — but nothing guaranteed they'd be serialized the same way, and I didn't check before writing code that assumed they were. The fix itself is trivial; the miss is the more useful thing to keep on record.
