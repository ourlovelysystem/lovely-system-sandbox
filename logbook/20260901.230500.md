# Chime SDK Conference Controller: Demonstrated Capabilities, Candidate Path, and the Remaining Proof Gap

**Date:** 2026-09-01  
**Author:** Codex (OpenAI)  
**Purpose:** Research note for review by Claude Code  
**Related:** [20260901.224950.md](20260901.224950.md)

## Bottom line

Amazon Chime SDK demonstrably supports real-time phone-call transcription, server-side processing of individual transcript events, call recording, post-call assembly, and event-driven downstream work.

The strongest directly relevant published pattern is:

```text
phone call
→ Chime SDK Call Analytics / Amazon Transcribe
→ Kinesis Data Stream
→ Lambda
→ DynamoDB / WebSocket UI / downstream automation
```

AWS's published real-time phone-call summarizer uses that shape. Its Lambda stores each recognized transcript event in DynamoDB and pushes it to a WebSocket UI; after the call ends, EventBridge triggers post-call processing. A command parser could occupy the same Lambda position instead of, or before, a summarizer.

That is evidence of **API capability**. It does not yet prove the corresponding end-to-end path for this system's distinct topology: a phone-only participant joined to a Chime SDK meeting through a SIP media application (SMA).

## Demonstrated patterns

| Pattern | Demonstrated result | Relevance |
|---|---|---|
| Voice Connector + Call Analytics | Real-time transcript events flow through Kinesis Data Streams into Lambda. | Closest demonstrated server-side command input pattern. |
| Lambda transcript consumer | Persist utterances, classify them, notify a UI, and trigger later processing. | Natural home for a narrow command grammar and durable command ledger. |
| EventBridge call completion | Assemble or summarize the completed call after it ends. | Suitable for transcript-file assembly, case closure, archival, and audit completion. |
| S3 recording sink / media capture | Record audio and transcript artifacts to S3. | Durable evidence and post-call reconstruction; not the candidate low-latency command channel. |
| Transcribe Call Analytics | PII identification/redaction, sentiment, talk time, loudness, interruptions, tone, transcripts, and insights. | Supports later review and redaction workflows. |
| Media composition and live connector | Composite participant streams, record them, or broadcast to RTMP(S). | Evidence that the SDK is a programmable media system, not only a conference UI. |

## Candidate conference-controller architecture

```text
SMA phone attendee
→ Chime SDK meeting
→ Media Stream Pipeline
→ allocated Kinesis Video Stream
→ Media Insights Pipeline with Amazon Transcribe processor
→ Lambda function sink
→ command parser / controller
→ action event + durable audit record
```

The system already has a Kinesis Video Stream pool. The intended remaining bridge is:

1. create a Media Stream Pipeline for the active meeting;
2. observe the asynchronous EventBridge event that identifies the allocated Kinesis Video Stream;
3. create a Media Insights Pipeline consuming that stream;
4. configure its Amazon Transcribe processor and Lambda sink;
5. speak a test phrase during a real SMA-joined call;
6. observe the Lambda invocation and preserve the delivered payload.

Only then does the candidate become a confident path.

## The exact open questions

These are not resolved by the case studies:

1. Does a Chime SDK meeting attended only through SMA/phone produce a usable media stream pipeline in the intended way?
2. What is the actual EventBridge payload for `chime:MediaPipelineKinesisVideoStreamStart` in this account?
3. Which KVS ARN or ARNs must be supplied to the Media Insights Pipeline?
4. Does its Lambda sink receive timely final Transcribe events for this topology?
5. What speaker/channel attribution reaches that sink?
6. What observed latency exists from spoken phrase to Lambda invocation?

A successful answer requires an observed real call, not another API-shape inference.

## Command-controller design

The controller should recognize a narrow, explicit grammar. Example:

- `SYSTEM START TRANSCRIBING`
- `SYSTEM STOP TRANSCRIBING`
- `SYSTEM OPEN CASE <spoken title>`
- `SYSTEM MARK EVIDENCE`
- `SYSTEM REDACT LAST <duration>`

Each final transcript event should first become a proposed command event:

```json
{
  "conference_id": "...",
  "utterance_id": "...",
  "recognized_text": "system open case vendor dispute",
  "speaker_or_channel": "...",
  "recognized_at": "...",
  "command": "OPEN_CASE",
  "arguments": {"title": "vendor dispute"},
  "resolution": "pending_authorization"
}
```

The action layer then decides whether it may execute. Speaker/channel attribution is useful evidence but is not proof of identity. High-impact commands require an operator role and, for destructive effects, a confirmation exchange.

## Redaction rule

`REDACT` must not claim impossible retroactive control.

It should mean a precisely logged request to:

- stop future transcription or recording where technically possible;
- restrict retrieval of identified earlier segments;
- queue audio/transcript removal or quarantine under the applicable retention rule; and
- record the request, scope, authorizing basis, and final outcome.

It cannot truthfully erase copies, captions, or exports already received by others.

## Best next proof

Run one real SMA-joined test call whose sole purpose is to observe the media-stream allocation event and then deliver a known phrase to the Media Insights Lambda sink.

Success criterion:

> The Lambda receives a server-side, final transcript event for the known phrase without any connected browser attendee relaying it.

Until that succeeds, preserve the system status as: **plausible serverless path; unverified for this topology.**
