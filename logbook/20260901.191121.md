# Building the media capture pipeline: two ForbiddenExceptions, both from undocumented caller-permission requirements

**Author:** Claude (Anthropic, Claude Code)
**Related:** [docs/party-line-helpdesk-spec.md](../docs/party-line-helpdesk-spec.md) — this work directly bears on the spec's "Second correction" section (transcript delivery via a client-SDK bot), but the spec has not been updated to reflect it. Per the operator's explicit instruction earlier in this project — "You should not be updating the spec without my input." — that correction is being surfaced here, not written into the spec.

## What happened

The operator said: "I want you to build the pipeline. That will verify it nice and good." — referring to a Chime SDK Media Capture Pipeline, needed to actually produce a transcript file in S3 (live meeting transcription alone, already built, only delivers transcript content to a connected client — it produces no file by itself).

Checked the actual `create-media-capture-pipeline` CLI help output directly rather than trusting prior claims: `ChimeSdkMeetingConfiguration.ArtifactsConfiguration` has no transcription-related field at all — only `Audio`, `Video`, `Content`, `CompositedVideo`. This contradicted the operator-relayed ChatGPT and Grok claims that the pipeline has an explicit "transcription message capture" toggle. Fetched the real AWS doc page (`transcription-messages.html`) directly to resolve the contradiction: the `transcription-messages/` folder is not a configurable option — it appears automatically in a media capture pipeline's S3 output whenever live transcription is active on the same meeting the pipeline is attached to. No flag exists because none is needed.

Built the pipeline: a new S3 bucket (`PartyLineCaptureBucket`) with the exact bucket policy AWS's own docs specify for the `mediapipelines.chime.amazonaws.com` service principal, a `CreateMediaCapturePipelineCommand` call added to `sma.js` right after `CreateAttendee`, sourced on the meeting's `MeetingArn`, sunk to the new bucket. Also created the account's `AWSServiceRoleForAmazonChimeSDKMediaPipelines` service-linked role, which didn't exist yet and is a hard prerequisite.

First deploy: the operator called in and reported "Now it's hanging up on me." CloudWatch logs showed the Lambda invocation itself was crashing on an uncaught `ForbiddenException: Insufficient permission to access S3 bucket` from the `CreateMediaCapturePipelineCommand` call — not a bucket-policy problem (the same call succeeded immediately when run from my own CLI credentials against the same bucket, same policy, same account). Diagnosed as the Lambda's own execution role having no S3 permissions at all on the new bucket — only the media pipelines service-linked role had access, via the bucket policy. Added an `S3CrudPolicy` for the capture bucket to the Lambda's role and redeployed.

Second deploy: the operator called again and reported "Hung up on me again." Same exact `ForbiddenException`, same message, despite the new S3CrudPolicy being confirmed present on the role (read back via `iam get-role-policy` before telling the operator to retry — the check that should have caught this before wasting a live call). Went back to AWS documentation specifically rather than guessing again, and found the actual, narrow cause in `create-pipeline.html`: "Your IAM role must also have permission to call the Amazon S3 `GetBucketPolicy` API on all resources." This is not part of any managed S3 policy template (not in SAM's `S3CrudPolicy`, not implied by any bucket-scoped grant) — it's a bare, bucket-policy-read permission the *caller* needs so Chime can verify the bucket policy before creating the pipeline, entirely separate from the runtime write access the service-linked role gets from the bucket policy itself. Added `s3:GetBucketPolicy` on `Resource: "*"` to the Lambda's role and redeployed. As of this entry, that third deploy has not yet been verified against a live call.

## Commentary

*(Claude.)* Two different `ForbiddenException`s, identical error text both times, two completely different root causes — one a missing grant on a bucket the Lambda never even writes to directly, the other a bare API-read permission with no relationship to the actual S3 write path at all. The error message doesn't distinguish between them; only the AWS documentation does, and only if read specifically rather than inferred from the shape of the previous fix. The second failure happened because I let the first fix's success pattern ("add an S3 permission, it'll work") stand in for actually reading what `CreateMediaCapturePipeline` requires from a caller — I verified the policy was *attached* before the second call, but I didn't verify it was the *right* policy, because I hadn't yet gone back to the doc that names `GetBucketPolicy` specifically. Two live calls were burned confirming the same wrong-permission-shaped guess twice in slightly different clothes. The fix this time came only from deliberately searching for the caller-permissions doc rather than pattern-matching from the first incident.
