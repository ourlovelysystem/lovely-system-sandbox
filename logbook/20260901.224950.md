# Real-time voice trigger: no confident path found yet, corrected my own architecture choice mid-investigation

**Author:** Claude (Anthropic, Claude Code)
**Related:** [20260901.202110.md](20260901.202110.md) — this entry picks up where that one left off, moving from the verified transcript pipeline to the next feature: a voice-triggered event.

## What happened

The operator asked for the alpha target's remaining piece: a caller speaking a trigger phrase ("drum roll please" — proposed and accepted as the phrase, `PlayAudio` of a real drum-roll sound as the action) should cause an immediate, server-side response. Two mechanisms were presented as a choice: polling the S3 transcript files the media capture pipeline already produces (seconds of latency, built on infrastructure already verified working), or a genuinely real-time path. The operator chose real time.

**First architecture proposed was wrong, and the operator caught it before any work started.** The first answer described a headless-browser bot (Puppeteer + Chrome, on ECS/Fargate, using AWS's `amazon-chime-sdk-recording-demo` sample as the reference pattern) as the only way to receive live transcript content server-side, since that content is documented as being delivered only to a connected client-SDK participant. The operator's response: "I don't know if you are looking in the right place. This does not sound correct to me." That was correct — a second look at API surface already touched earlier in the day (`chime-sdk-media-pipelines`) turned up `CreateMediaStreamPipeline` (streams a Chime SDK meeting's live audio to a Kinesis Video Stream) and `CreateMediaInsightsPipeline` (runs a Transcribe processor against a KVS stream and sinks results directly to a Lambda, SQS, or SNS) — a fully serverless path with no browser, no container, that had been looked at hours earlier while researching the capture pipeline and set aside without connecting the two halves.

**That corrected path also isn't confirmed working.** Researched and verified individually, via CLI help output and AWS documentation fetched directly (not inferred): the `CreateMediaStreamPipeline` and `CreateMediaInsightsPipeline` API shapes, and the complete IAM policy (trust policy plus permissions, including the `LambdaFunctionSink`-specific `lambda:InvokeFunction`/`lambda:GetPolicy` statement) required for the insights pipeline's `ResourceAccessRoleArn`. A Kinesis Video Stream pool was created live in the account (`arn:aws:chime:us-east-1:867712763388:media-pipeline-kinesis-video-stream-pool/lovely-system-sandbox-partyline-kvs-pool`) as the one-time prerequisite resource. But the chain has a real gap: `CreateMediaStreamPipeline`'s response does not return the actual Kinesis Video Stream ARN that gets allocated — per AWS's documentation, that ARN is only delivered later, asynchronously, via an EventBridge event (`chime:MediaPipelineKinesisVideoStreamStart`), whose exact payload shape has not actually been seen (only AWS's prose description of its existence). Whether this whole chain behaves identically for a meeting attendee that joined via the SMA's `JoinChimeMeeting` action (phone-bridged, no browser) versus a native browser client attendee is also unconfirmed — nothing in the documentation says it wouldn't, but nothing confirms it does, and three separate "should work per the docs, didn't on the first real call" surprises happened earlier today alone.

**Externally-sourced advice was checked and found to share the same gap it didn't acknowledge.** The operator pasted a third-party technical writeup (unattributed) proposing a "small service reads final transcript lines" as if that were a simple, separate component. Checked against what's actually been verified: that "small service" is only possible by being a connected client-SDK participant — the advice implicitly assumes a web/mobile app is the primary host with phone dial-in as an optional add-on ("Host: Amazon Chime SDK Meetings (web/mobile). Add Voice Connector + SIP media application only if people also dial a phone number"), which is the reverse of this project's actual shape: phone-only, no browser client anywhere. The advice wasn't wrong about the pieces it named (correctly ruled out Lex/`StartBotConversation` for the same reason already established here; correctly named `CreateMediaConcatenationPipeline` as a genuinely useful, not-yet-investigated API for producing one clean audio file per call), but it didn't solve, or even name, the actual open problem.

The operator's own assessment, stated plainly: "I don't think we have a confident path right now." Agreed, explicitly, rather than defended. A complete problem statement was then written up for the operator to run past other AI agents, laying out the verified system shape, the exact unresolved gap, and specific questions for outside review.

## Commentary

*(Claude.)* The corrected-mid-investigation moment is worth being precise about, because it's a repeat of the same failure shape as the S3-bucket-permission incident earlier today, just one layer up: I had already looked directly at the right API (`create-media-insights-pipeline` help output, hours earlier, complete with its `LambdaFunctionSinkConfiguration` sink) and set it aside because at the time I only had half the picture — I didn't yet know `CreateMediaStreamPipeline` was the piece that produces the KVS stream that `CreateMediaInsightsPipeline` consumes. The information needed to get this right the first time was already in hand; it just hadn't been connected. The operator's skepticism ("this does not sound correct") is what triggered going back and finding the connection, not anything in my own process — I was prepared to start building the ECS/Puppeteer version without it.

The second miss — accepting a pasted external answer's framing at face value long enough to have to check it — is smaller, but the same shape again: an answer that sounds complete because it names real APIs correctly is not the same as an answer that actually addresses the specific constraint of this system. "Clients get TranscriptEvent" is true and also does nothing to tell you how to get a client where none exists.
